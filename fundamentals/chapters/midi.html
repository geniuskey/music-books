Chapter 16

MIDI와 음악 데이터

MIDI는 소리가 아니라 연주 동작을 보내는 프로토콜입니다. "60번 건반을 세기 100으로 눌렀다", "페달을 밟았다" 같은 사건이 3바이트 남짓한 메시지로 오갑니다. 1983년에 정한 31.25 kbaud 직렬 규격이 40년 넘게 거의 그대로 쓰이고 있다는 점에서, MIDI는 공학사에서 보기 드문 장수 인터페이스입니다. 이 장에서는 그 바이트를 직접 만들고, 해독하고, 파일로 저장하고, 다시 소리로 바꿉니다.

  • MIDI 1.0의 물리 계층(31.25 kbaud, 8-N-1)에서 바이트당 320 µs를 계산하고, 화음 번짐(chord smear)을 예측한다.
  • 상태 바이트와 데이터 바이트(MSB)로 메시지를 구분하고, 노트 온/오프·CC·프로그램 체인지·피치 벤드·애프터터치를 손으로 인코딩한다.
  • 러닝 스테이터스, 실시간 메시지 끼어들기, SysEx를 처리하는 스트림 파서를 이해한다.
  • 14비트 피치 벤드의 분해능과 벤드 범위(RPN 0)의 관계를 계산한다.
  • 표준 MIDI 파일(MThd/MTrk)의 가변 길이 수(VLQ), PPQ, 템포 메타 이벤트로 틱과 초를 상호 변환하고, 실제 .mid 파일을 만든다.
  • MPE, MIDI 2.0(UMP), OSC, Web MIDI API의 위치를 안다.

1983년의 31.25 kbaud

1981년 시퀀셜 서킷의 데이브 스미스와 롤랜드의 가케하시 이쿠타로가 제안한 범용 신시사이저 인터페이스는 1983년 1월 NAMM 쇼에서 두 회사의 신시사이저(Prophet-600과 JX-3P)를 케이블 한 가닥으로 연결해 시연되었고, 같은 해 MIDI 1.0 규격으로 발표되었습니다. 규격은 지금 미국의 MMA(MIDI Manufacturers Association, 현재 MIDI Association)와 일본의 AMEI가 함께 관리합니다.

물리 계층은 5핀 DIN 커넥터와 5 mA 전류 루프입니다. 수신 측은 옵토아이솔레이터로 전기적으로 절연되어 있어 접지 루프 험이 생기지 않습니다. 직렬 형식은 비동기 UART 그대로입니다: 시작 비트 1 + 데이터 8비트(LSB 먼저) + 정지 비트 1 = 10비트/바이트. 전송 속도 31,250 bit/s는 당시 흔하던 1 MHz 클록을 32로 나눈 값이어서 정해졌습니다.

$$t_{\text{byte}} = \frac{10\ \text{bit}}{31\,250\ \text{bit/s}} = 320\ \mu\text{s}, \qquad t_{\text{Note On}} = 3 \times 320\ \mu\text{s} = 0.96\ \text{ms}, \qquad R_{\max} = 3\,125\ \text{byte/s}$$
한 케이블의 최대 처리량은 초당 약 1,000개의 노트 온 메시지다. 10음 화음을 '동시에' 누르면 마지막 음은 첫 음보다 약 9 ms(러닝 스테이터스를 쓰면 약 6 ms) 늦게 도착한다. 이 지연을 화음 번짐(Chord Smear)이라 한다.

메시지의 해부: 상태 바이트와 데이터 바이트

MIDI 바이트는 최상위 비트(MSB)로 두 종류로 나뉩니다. MSB가 1(0x80–0xFF)이면 상태 바이트(Status Byte)로 메시지 종류를 알리고, MSB가 0(0x00–0x7F)이면 데이터 바이트(Data Byte)입니다. 그래서 모든 데이터 값은 7비트, 즉 0–127이고, 수신기는 스트림 중간에 끼어들어도 다음 상태 바이트에서 즉시 동기를 다시 잡을 수 있습니다(자기 동기화 부호). 채널 메시지의 상태 바이트는 위 4비트가 종류, 아래 4비트가 채널(0–15, 사람에게는 1–16으로 표시)입니다.

노트 번호는 반음 단위의 선형 눈금이고, 평균율 A4 = 440 Hz 기준으로 주파수는 다음과 같습니다(5장). 0번은 C−1(8.18 Hz), 127번은 G9(12,543.9 Hz)로 피아노 88건반(21–108번)을 넉넉히 덮습니다.

$$f(n) = 440 \cdot 2^{(n-69)/12}\ \text{Hz}, \qquad n = 69 + 12\log_2\frac{f}{440}$$
60번을 이 책처럼 C4라 부르는 것이 과학적 음높이 표기(SPN)지만, 야마하 계열 장비와 일부 DAW는 60번을 C3로 표시한다. 같은 바이트 0x3C에 이름만 한 옥타브 다르게 붙는 것이라, 장비 설명서를 볼 때 늘 확인해야 한다.

벨로시티는 건반이 눌린 속도(대개 두 접점 사이 통과 시간)를 1–127로 양자화한 값입니다. 규격은 세기→음량 곡선을 정하지 않지만, 흔히 진폭을 \((v/127)^2\)에 비례하게(약 \(40\log_{10}(v/127)\) dB) 둡니다. 이 장의 멜로디 합성기는 확인하기 쉬운 소리를 위해 피크 이득 0.28(v/127)²+0.015를 사용하므로 순수 제곱 곡선과 달리 작은 벨로시티에도 바닥 이득이 있습니다.

러닝 스테이터스와 시스템 메시지

    
대역폭을 아끼기 위해 MIDI 1.0은 러닝 스테이터스(Running Status)를 허용합니다. 같은 상태 바이트가 이어지면 두 번째부터 생략하고 데이터 바이트만 보냅니다. 수신기는 마지막 채널 상태 바이트를 기억해 두었다가 상태 없이 들어온 데이터에 적용합니다. 노트 오프를 '세기 0인 노트 온'으로 보내는 관례는 바로 이 러닝 스테이터스를 끊지 않기 위한 것입니다.

    
$$\underbrace{\texttt{90 3C 64}}_{\text{C4 on}}\ \underbrace{\texttt{40 64}}_{\text{E4 on}}\ \underbrace{\texttt{43 64}}_{\text{G4 on}}\ \cdots\ \underbrace{\texttt{3C 00}}_{\text{C4 off}} \qquad \text{바이트 수: } 3 + 2(N-1)$$
      
스트림 파서의 규칙: ① 채널 상태 바이트(80–EF)는 러닝 스테이터스를 갱신한다. ② 시스템 공통 메시지(F0–F7)는 러닝 스테이터스를 지운다. ③ 실시간 메시지(F8–FF)는 한 바이트짜리로, 다른 메시지의 데이터 바이트 사이에도 끼어들 수 있으며 러닝 스테이터스에 영향을 주지 않는다. ④ SysEx는 F0으로 시작해 F7(EOX)로 끝나며 사이에는 7비트 데이터만 온다.

피치 벤드와 해상도

    
피치 벤드는 MIDI 1.0에서 드물게 처음부터 14비트인 메시지입니다. 두 데이터 바이트 중 LSB가 먼저 옵니다. 값 0–16383의 중앙 8192(E0 00 40)가 '벤드 없음'이고, 실제 음높이 변화는 수신기의 벤드 범위에 달려 있습니다. 기본값은 ±2반음이며 RPN 0으로 바꿉니다(B0 65 00 B0 64 00 B0 06 0C = ±12반음).

    
$$v = 128\cdot\text{MSB} + \text{LSB}, \qquad \Delta c = \frac{v-8192}{8192}\times 100R\ \text{cent}, \qquad \text{분해능} = \frac{200R}{2^{b}}\ \text{cent/단계}$$
      
\(R\): 벤드 범위(반음), \(b\): 실제로 쓰는 비트 수. \(R=2\), 14비트면 0.024 ¢/단계로 충분히 매끄럽다. 그러나 MSB만 보내는(7비트) 컨트롤러는 3.1 ¢/단계, \(R=12\)이면 18.75 ¢/단계로, 느린 글리산도에서 계단(zipper)이 들린다. 음높이 변별 한계(JND)는 중간 음역에서 약 5–10 ¢다. 양의 최댓값은 8191이라 \(+R\)에 1단계 모자라는 비대칭도 있다.

클럭과 동기

    
여러 장비가 같은 템포로 움직이려면 시간을 공유해야 합니다. MIDI 클럭은 가장 단순한 방법으로, 마스터가 4분음표당 24번(24 PPQN, pulses per quarter note) F8 한 바이트를 보냅니다. 슬레이브는 펄스 간격으로 템포를 추정하고, FA(스타트)·FC(스톱)·F2(송 포지션)로 운전합니다. 템포 값 자체는 보내지 않으므로, 슬레이브는 결국 잡음 섞인 주기 측정으로 BPM을 추정하는 문제를 풀게 됩니다.

    
$$T_{\text{tick}} = \frac{60}{24\cdot\text{BPM}}\ \text{s}\quad(120\ \text{BPM에서 } 20.83\ \text{ms}), \qquad \widehat{\text{BPM}}_k = \frac{60}{24\,\overline{\Delta t}_k}$$
      
수신 시각의 지터가 \(\sigma_j\)이면 한 간격의 측정 오차는 \(\sqrt2\,\sigma_j\)이고, 1 ms 지터만으로도 순간 추정 BPM은 120 ± 8 정도로 흔들린다. \(N\)개 간격을 평균하면(이동 평균) 끝점만 남으므로 오차가 \(1/N\)로 줄지만 템포 변화에 늦게 반응한다. 실제 장비는 PLL(위상 고정 루프)로 이 트레이드오프를 조정한다.

표준 MIDI 파일: 틱, VLQ, 템포 맵

    
케이블의 MIDI는 '지금' 일어나는 사건이지만, 파일에는 언제를 함께 적어야 합니다. 1988년의 표준 MIDI 파일(Standard MIDI File, SMF)은 청크 구조로 되어 있습니다. 헤더 청크 MThd 하나와 트랙 청크 MTrk 여러 개이며, 모든 정수는 빅 엔디언입니다.

    
    
Δt는 대부분 작지만 가끔 아주 큽니다(긴 쉼표). 그래서 SMF는 가변 길이 수(Variable-Length Quantity, VLQ)를 씁니다. 7비트씩 끊어 큰 자리부터 내보내고, 마지막 바이트를 뺀 모든 바이트의 MSB를 1(계속)로 둡니다. 0–127은 1바이트, 최대 0x0FFFFFFF는 4바이트입니다. 같은 발상이 UTF-8, Protocol Buffers의 varint, LEB128에도 쓰입니다(바이트 순서는 다름).

    

      
값VLQ 바이트값VLQ 바이트

0x7F7F0x400081 80 00

        
0x8081 000x1FFFFFFF FF 7F

        
0x2000C0 000x0FFFFFFFFF FF FF 7F

      
    

    
틱을 초로 바꾸려면 템포가 필요합니다. 템포는 메타 이벤트 FF 51 03 tt tt tt에 4분음표 하나의 마이크로초(24비트)로 적힙니다. BPM이 아니라 주기를 적는 것은 정수로 정밀하게 쓰기 위해서입니다. 템포가 곡 중간에 바뀌면 구간별로 나눠 더합니다(템포 맵).

    
$$\mu = \frac{60\,000\,000}{\text{BPM}}, \qquad t(\text{tick}) = \sum_{j} \frac{\big(\min(\text{tick}, k_{j+1}) - k_j\big)^{+}\,\mu_j}{\text{PPQ}\cdot10^{6}}\ \text{s}$$
      
\(k_j\): \(j\)번째 템포 이벤트의 틱 위치, \(\mu_j\): 그 구간의 µs/4분음표. 예) PPQ 480, 120 BPM에서 1틱 = 500,000/480 ≈ 1.04 ms. 960 PPQ면 약 0.52 ms로, 사람의 타이밍 변별(수 ms)보다 충분히 세밀하다.

브라우저에서 MIDI: Web MIDI API

    
W3C의 Web MIDI API는 자바스크립트에서 운영체제의 MIDI 포트에 직접 접근하게 해 줍니다. 보안 컨텍스트(https 또는 localhost)에서만 동작하고, 사용자 권한 확인을 거치며, SysEx는 별도 권한({sysex: true})이 필요합니다. 2024년 기준 크롬·엣지·오페라 등 크로미움 계열과 파이어폭스(108 이후, 사이트 권한 애드온 방식)가 지원하고, 사파리는 지원하지 않습니다.

    
const access = await navigator.requestMIDIAccess();      // 권한 요청
for (const input of access.inputs.values())
  input.onmidimessage = (e) => {                          // e.data: Uint8Array, e.timeStamp: ms
    const [st, d1, d2] = e.data;
    if ((st & 0xF0) === 0x90 && d2 > 0) noteOn(st & 0x0F, d1, d2);
  };
const out = [...access.outputs.values()][0];
out.send([0x90, 60, 100]);  out.send([0x80, 60, 0], performance.now() + 500);  // 타임스탬프 예약

    
브라우저가 바이트 스트림을 이미 메시지 단위로 잘라서(러닝 스테이터스 복원 포함) 넘겨 주므로, 3절의 파서는 직렬 포트나 파일을 다룰 때 필요합니다. 출력의 send(data, timestamp)는 performance.now() 기준으로 미래 시각을 지정할 수 있어, 웹 오디오의 '앞서 예약하기'(11장의 스케줄러)와 같은 방식으로 정확한 타이밍을 얻습니다.

핵심 정리

    
    
      
  1. MIDI 1.0은 31.25 kbaud, 8-N-1 직렬이다. 바이트당 320 µs, 노트 온 하나에 약 1 ms가 걸려 큰 화음은 수 ms 번진다.
    2. 
      
  2. MSB가 1이면 상태, 0이면 데이터 바이트다. 데이터는 7비트이고, 채널 메시지 상태 바이트는 '종류 니블 + 채널 니블'이다. 세기 0인 노트 온은 노트 오프다.
    3. 
      
  3. 러닝 스테이터스는 같은 상태 바이트를 생략한다. 실시간 메시지(F8–FF)는 어디든 끼어들 수 있고 러닝 스테이터스를 지우지 않으며, 시스템 공통 메시지는 지운다.
    4. 
      
  4. 피치 벤드는 LSB 먼저인 14비트 값(중앙 8192)이다. 분해능은 200R/2^b ¢이므로, 벤드 범위가 넓거나 7비트만 쓰면 계단이 들린다.
    5. 
      
  5. MIDI 클럭은 4분음표당 24개의 F8이다. 템포는 펄스 간격에서 추정하므로 지터와 반응 속도 사이의 트레이드오프가 생긴다.
    6. 
      
  6. SMF는 MThd + MTrk 청크이고, 이벤트마다 VLQ로 Δt(틱)가 붙는다. 시간 = 틱 × (µs/4분음표) / PPQ를 템포 맵 구간별로 더한 것이다.
    7. 
      
  7. GM은 128음색과 10번 채널 드럼 배치를 표준화했고, MPE·MIDI 2.0·OSC는 음별 표현, 고해상도, 양방향성, 네트워크로 MIDI 1.0의 한계를 넘는다.
    8. 
    

  


  

    
확인 퀴즈

    

      
3번 채널에서 E4(64)를 세기 80으로 누르는 노트 온 메시지는?

        
      
채널 3은 아래 니블 2(0부터 셈)이므로 상태 0x92. 64 = 0x40, 80 = 0x50. 데이터 바이트에 0x80을 쓰면 MSB가 1이라 상태 바이트로 오인된다.

      
러닝 스테이터스를 써서 같은 채널로 노트 온 6개를 보낼 때 필요한 바이트 수와 전송 시간은?

        
      
첫 메시지 3바이트 + 나머지 5개 × 2바이트 = 13바이트. 바이트당 10비트 / 31,250 bit/s = 320 µs이므로 13 × 0.32 = 4.16 ms.

      
피치 벤드 메시지 E0 00 60은 벤드 범위 ±2반음에서 몇 센트인가?

        
      
v = 0x60 × 128 + 0x00 = 96 × 128 = 12288. (12288 − 8192)/8192 = 0.5이므로 0.5 × 200 ¢ = +100 ¢, 즉 반음 하나 위.

      
값 200을 VLQ로 인코딩하면?

        
      
200 = 1·128 + 72. 큰 자리 7비트 1에 계속 비트를 붙여 0x81, 마지막 7비트 72 = 0x48은 MSB 0. 그래서 81 48.

      
PPQ 480, 템포 메타 이벤트 FF 51 03 09 27 C0(600,000 µs)일 때 960틱은 몇 초인가?

        
      
960틱 = 4분음표 2개. 4분음표 하나가 0.6 s(100 BPM)이므로 1.2 s.

      
MIDI 클럭(F8)으로 120 BPM을 보낼 때 클럭 바이트 간격과 그것이 쓰는 대역폭 비율에 가장 가까운 것은?

        
      
초당 120/60 × 24 = 48개, 간격 1/48 s = 20.8 ms. 48바이트/s ÷ 3,125바이트/s ≈ 1.5%.
